# هوشمندی قیمت، مسیر تماس/چت هر پلتفرم، استعلام خودکار، خروجی تفکیک‌شده

> تاریخ: ۱۴۰۵/۰۶/۰۶ (۲۰۲۶-۰۸-۲۸)
> وضعیت: **فقط مستند فنی** — تا تأیید، کدنویسی شروع نمی‌شود
> وابسته: `docs/multi-platform-sheypoor-ring.md` · `docs/price-hunter-product.md`
> هدف: وقتی محصول به بازار می‌رود، «ارزون» دروغ نگوید، معیوب را با ارزان قاطی نکند، هزارتومانِ توافقی را شکار نکند، و برای هر سایت مسیر تماس درست را خودش انتخاب کند.

---

## ۰) اصل محصول

شکارچی حرفه‌ای این سه را **هرگز یکی حساب نمی‌کند**:

| واقعیت آگهی | الان در ۲.۱.۲۵ | باید بشود |
|---|---|---|
| گوشی سالم ۳۲ م در برابر میانه ۴۸ م | اگر داخل بازه باشد VIP | **خیلی مناسب** |
| همان مدل، LCD شکسته، ۱۲ م | اگر داخل بازه باشد VIP | **معیوب** — شکار قیمت نیست |
| قیمت روی آگهی `۱٬۰۰۰` چون فروشنده توافقی می‌گذارد | اگر بازه باشد معمولاً رد؛ اگر نباشد ذخیره می‌شود | **استعلام** — تا قیمت نقد نیاید ویژه نشود |
| «خریدار گوشی معیوب» | ممکن است سرنخ شود | **حذف** |

رینگ در FAQ خودش می‌گوید قیمت خیلی پایین نشانه کلاهبرداری است. اگر ما همان را «ویژه» کنیم، محصول فروش‌نرفتنی است.

دو موتور پیام باید **جدا** باشند؛ هر دو در محصول بعدی **خودکار**اند (با تیک و سقف)، روی دیوار و شیپور و رینگ:

1. **استعلام قیمت** — یک سؤال کوتاه برای آگهی‌هایی که عدد واقعی ندارند.
2. **پیام بازاریابی** — قالب تب پیام‌ها به فقط‌چت؛ قالب پیامک به شماره‌دار.

پاسخ هر دو کانال خوانده و فهمیده می‌شود. جزئیات ارسال خودکار + NLU: `docs/auto-chat-sms-nlu.md`.

قاقی‌کردن قالب استعلام با قالب بازاریابی = بن اکانت + ویژهٔ دروغ.

## ۱) لوله تصمیم (از کشف تا ویژه یا استعلام)

هر آگهی جدید، قبل از تلگرام و قبل از صف شماره، از این لایه‌ها رد می‌شود. لایه بالاتر اگر حکم قطعی داد، لایه‌های بعدی برای «ویژه» اجرا نمی‌شوند.

```
کشف آگهی (دیوار / شیپور / رینگ)
        │
   [L0] نقش: فروشنده یا خریدار؟
        │ خریدار → حذف (کلاس buyer)
        ▼
   [L1] وضعیت کالا: نو / درحدنو / کارکرده / معیوب / نامشخص
        │ معیوب قطعی → کلاس defective — ذخیره در سطل معیوب، ویژه نه
        ▼
   [L2] نوع قیمت: نقد / توافقی / جای‌نگهدار / اقساط / معاوضه / رایگان / نامشخص
        │ جای‌نگهدار یا توافقی بدون عدد → کلاس inquire — ویژه نه تا استعلام
        ▼
   [L3] عقل سلیم دسته (کف قیمت دسته)
        │ زیر کف بدون نشانه معیوب → inquire یا suspicious
        ▼
   [L4] امتیاز شکار نسبت به میانه (فقط نقد + غیرمعیوب)
        │ مناسب / خیلی‌مناسب / بازار / مشکوک‌ارزان
        ▼
   [L5] انتخاب مسیر تماس (پلتفرم × حالت تماس)
        │ phone و/یا chat
        ▼
   [L6] اگر inquire: استعلام (چت یا پیامک سؤال) → صبر پاسخ
        ▼
   [L7] پارس پاسخ → قیمت واقعی / اعتراف معیوب → برگشت به L1–L4
        │
        └── ویژه فقط اگر بعد از L7 هنوز نقد سالم و زیر میانه باشد
```

هیچ آگهی با قیمت `۱۰۰۰` یا متن «معیوب» نباید بدون عبور از این لوله تگ VIP بگیرد.

## ۲) لایه L0 — خریدار در برابر فروشنده

حذف قطعی اگر عنوان یا توضیح با این‌ها شروع شود یا هسته جمله باشد:

`خریدار`، `میخرم`، `می‌خرم`، `خرید نقد`، `خریدار گوشی`، `خریدار معیوب`، `خریدار شکسته`، `نقد خریدارم`

نمونه زنده شیپور: «خریدار گوشی شکسته معیوب در ساری» — قیمت توافقی. این شکار نیست.

خروجی: `role = seller | buyer` — buyer ذخیره نشود یا فقط در لاگ تشخیص fore آمار.

## ۳) لایه L1 — معیوب بودن (دلیل قیمت پایین)

دو منبع؛ منبع ساخت‌یافته همیشه مقدم است.

### ۳.۱ فیلد ساخت‌یافته (بهترین سیگنال)

**شیپور — زنده روی صفحه آگهی تأیید شد:**

```
### وضعیت کالا
نو
```

نمونه: `Samsung Level U2` — ۱۲٬۰۰۰٬۰۰۰ تومان، وضعیت **نو**.

مقادیر مورد انتظار شیپور (باید در پیاده‌سازی از HTML/JSON همان بلوک خوانده شود، نه حدس سخت):

| مقدار روی سایت | کد داخلی | اثر شکار |
|---|---|---|
| نو | `new` | شکار آزاد |
| در حد نو / کارکرده کم | `like_new` | شکار آزاد |
| کارکرده | `used` | شکار آزاد (میانه جدا اگر نمونه کافی) |
| نیازمند تعمیر / معیوب / اوراقی | `defective` | **هیچ‌گاه خیلی‌مناسب** |

دیوار: گاهی ویجت «وضعیت» در جزئیات آگهی؛ اگر نبود فقط واژگان.
رینگ: تا ضبط Flutter، فقط واژگان + بعداً فیلد معادل در DOM.

### ۳.۲ واژگان فارسی (عنوان + توضیح)

وزن **قطعی معیوب** (یکی کافی است → `defective`):

- معیوب، خراب، اوراقی، اسقاط، تصادفی (خودرو)، چپی، اتاق تعویض
- آب‌خوردگی، آبخورده، تعمیری، نیاز به تعمیر، راه‌انداز نیست، روشن نمیشه
- ال‌سی‌دی شکسته، LCD شکسته، تاچ خراب، گوشی شکسته، شیشه شکسته
- سوخته، سوختگی برد، ایراد دارد، مشکل دارد (با احتیاط: «بدون ایراد» نفی است)
- لکلکی، رنگ‌شده کامل، شاسی ضربه‌خورده (خودرو)

وزن **مشکوک معیوب** (به‌تنهایی کافی نیست؛ با قیمت خیلی پایین → inquire یا defective_soft):

- خط و خش زیاد، افتادگی رنگ، یک بار تعمیر، تعویض قطعه، گارانتی ندارد

نفی‌ها که معیوب را باطل می‌کنند اگر همان جمله باشند:

- بدون ایراد، سالم، آکبند، در حد نو، بدون خط و خش، ضمانت سلامت

قواعد نفی:

- «بدون ایراد» در همان جمله بر «ایراد» می‌چربد.
- «معیوب» بدون نفی = قطعی.

### ۳.۳ واکنش سیستم برای معیوب

| عمل | بله/خیر |
|---|---|
| ذخیره در دیتابیس | بله — سطل `defective` |
| هشدار ویژه / خیلی‌مناسب | خیر |
| صف شماره اولویت شکار | خیر (اولویت عادی یا جدا «معیوب برای قطعه») |
| خروجی اکسل | شیت جدا «معیوب» |
| استعلام چت | خیر مگر کاربر تیک «معیوب را هم برای قطعه بخواه» |

قیمت پایین معیوب **توضیح دارد**؛ شکارچی نباید آن را فرصت سالم ببیند. این دقیقاً فرق محصول آماتور و قابل‌فروش است.

## ۴) لایه L2 — نوع قیمت و «هزار تومانِ توافقی»

### ۴.۱ گونه‌ها

| `price_kind` | تشخیص | ویژه؟ |
|---|---|---|
| `cash` | عدد معتبر در بازه عقل دسته | بله اگر شکار |
| `negotiable` | «توافقی»، «قیمتتوافقی»، «توافقی» بدون عدد | فقط بعد از استعلام |
| `placeholder` | عدد ساختگی (پایین) | استعلام؛ ویژه تا پاسخ نه |
| `installment` | اقساط، پیش‌پرداخت، چک | پیش‌فرض رد شکار |
| `swap` | معاوضه، پایه‌به‌پای | رد شکار |
| `free` | رایگان، واگذاری | سطل جدا |
| `unknown` | هیچ‌کدام | استعلام |

### ۴.۲ جای‌نگهدار — لیست قطعی + نسبی

فروشنده‌های ایرانی عمداً `۱۰۰۰` یا `۱۱۱۱` می‌گذارند تا فیلتر قیمت سایت را دور بزنند. این‌ها نقد نیستند.

**لیست مطلق** (اگر این عدد قیمت اعلامی باشد → `placeholder`):

`0`، `1`، `10`، `11`، `100`، `111`، `123`، `1000`، `1111`، `1234`، `11111`، `12345`، `10000`، `11000`، `111111`، `123456`

ارقام فارسی همان‌ها بعد از نرمال‌سازی.

**نسبی دسته** (حتی اگر در لیست مطلق نباشد):

```
اگر price_toman < 0.02 × میانه_دسته_شهر   و   نشان معیوب نیست
    → placeholder یا inquire
اگر price_toman < کف_سخت_دسته:
    موبایل < ۵۰۰ هزار
    لپ‌تاپ < ۱ میلیون
    خودرو سواری < ۵ میلیون
    → placeholder (مگر فیلد وضعیت=معیوب که می‌شود defective)
```

کف سخت قابل تنظیم است؛ اعداد بالا نقطه شروع محافظه‌کارانه‌اند.

**ترکیب با متن:**

- عدد کوچک + «توافقی» در عنوان → `placeholder` (نه cash)
- «قیمت روی عکس» / «تماس بگیرید قیمت» → `unknown` → inquire

نمونه زنده شیپور که نباید شکار شود: نوکیا فروشگاه `۴۰۰٬۰۰۰` وسط دسته موبایل با میانه ده‌ها میلیون — اگر کلمه پایش «آیفون» باشد اصلاً match نمی‌شود؛ اگر پایش کل دسته موبایل باشد باید `suspicious` یا خارج از مدل باشد نه VIP.

### ۴.۳ واکنش

```
cash + not defective     → برو L4 شکار
negotiable / placeholder / unknown → کلاس inquire
installment / swap       → رد شکار (قابل تیک)
defective                → سطل معیوب (L1 برده)
```

## ۵) لایه L4 — شکار فقط روی نقد سالم

فقط وقتی `role=seller` و `condition != defective` و `price_kind=cash` و `price_confidence=high`.

میانه از آگهی‌های **نقد سالم** همان پایش (۷۲ ساعت / حداقل ۳۰ نمونه). معیوب و جای‌نگهدار داخل میانه نروند وگرنه میانه خراب می‌شود.

| سطح | شرط پیشنهادی | هشدار |
|---|---|---|
| بازار | −۵٪ تا +۱۰٪ | نه |
| مناسب | ۱۰–۲۲٪ زیر میانه | آرام |
| خیلی‌مناسب | >۲۲٪ و ≤۴۵٪ زیر میانه | فوری + اول صف شماره |
| مشکوک‌ارزان | >۴۵٪ زیر بدون معیوب | **هشدار نده** — سطل مشکوک / استعلام سلامت |

اگر نمونه میانه کافی نیست: شکارچی «گرم نشده»؛ فقط فیلتر بازه دستی کار کند.

## ۶) لایه L5 — مسیر تماس؛ هر پلتفرم مال خودش

سیستم **یک روتِر تماس** دارد. کلاینت دیوار را برای شیپور/رینگ کپی نمی‌کنیم.

خروجی روتِر برای هر آگهی:

```
contact_mode: phone_and_chat | phone_only | chat_only | login_required | none
phone_status: pending | found | hidden | error | not_supported
chat_status: available | not_available | sent_inquiry | awaiting_reply | replied | failed
preferred_path: phone | chat | chromium_unknown
```

### ۶.۱ دیوار (مسیر فعلی، شناخته‌شده)

| کار | مسیر فنی زنده |
|---|---|
| شماره | لاگین JWT → `POST /v8/postcontact/web/contact_info_v2/{token}` با `contact_uuid` از `posts-v2` |
| خروجی شماره | `found` / `hidden` (صریحاً مخفی=فقط چت) / `error` (در صف می‌ماند) / `removed` |
| چت | داخل دیوار؛ پیشنهاد هوشمند جملات: «گوشی هنوز موجوده؟»، «قیمتش چنده؟» ([مستند دیوار](https://divar.ir/daal/newsroom/divar-chat-features)) |
| ارسال چت در ۲.۱.۲۵ | نیمه‌خودکار: قالب + باز کردن آگهی + Paste انسان |

انتخاب:

- اگر `found` → مسیر اصلی شماره (تماس/پیامک). چت اختیاری.
- اگر `hidden` → فقط چت. استعلام قیمت اگر لازم باشد از چت.
- ارسال انبوه خودکار چت بازاریابی: **ممنوع** (بن).

استعلام دیوار: ترجیح با کلیک پیشنهاد خود دیوار («قیمتش چنده؟») داخل همان پروفایل Chromium، نه متن اسپم سفارشی.

### ۶.۲ شیپور (زنده ۱۴۰۵/۰۶ — شبیه دیوار ولی API شماره عمومی نیست)

صفحه آگهی نمونه `/v/samsung-level-u2-466163319.html`:

- قیمت نقد روی صفحه: `۱۲,۰۰۰,۰۰۰`
- **وضعیت کالا: نو**
- شماره ماسک: `0912XXX4776 (نمایش کامل)` و «شماره تماس تایید شده»
- دکمه‌ها: `تماس با ۰۹۱۲XXX۴۷۷۶` · `چت با {نام فروشنده}`
- پایین صفحه: `اطلاعات تماس` · `چت`
- **چیپ سؤال آماده روی خود صفحه:** `سلام، وقت بخیر.` `هنوز موجوده؟` `قیمت چنده؟` `تخفیف داره؟`
- فروشنده: `/users/{id}`

نتیجه فنی:

| کار | مسیر صحیح شیپور |
|---|---|
| Discovery | HTML `/s/{شهر}/{دسته}?q=` بدون لاگین |
| وضعیت کالا | پارس بلوک «وضعیت کالا» قبل از هر شکار |
| شماره | بعد از لاگین `/session`، کلیک «نمایش کامل» در **همان پروفایل Chromium** — API عمومی پیدا نشد |
| چت | دکمه «چت با {نام}» در همان پروفایل |
| استعلام قیمت | **کلیک چیپ خود شیپور «قیمت چنده؟»** — بهترین مسیر؛ شبیه انسان، کم‌ریسک‌تر از متن سفارشی |

اگر بعد از لاگین هنوز ماسک ماند → `hidden` شیپور (معادل فقط‌چت دیوار).

لاگین شیپور OTP جدا است؛ کوکی `.sheypoor.com` در همان `accounts/<name>/chromium`.

سهمیه شماره شیپور از دیوار جدا است. ۴۰۳/کپچای شیپور فقط همان پلتفرم را برای آن اکانت می‌خواباند.

### ۶.۳ رینگ (متفاوت — چت‌اول)

شواهد:

- وب Flutter؛ HTML لیست خالی است.
- آگهی `/a/{id}`.
- UI قبلی: «برای گرفتن اطلاعات تماس کاربر ابتدا وارد شوید» → OTP ۶ رقمی → «اطلاعات تماس / تماس تلفنی».
- FAQ: معامله از طریق گفتگو؛ قیمت خیلی پایین را مشکوک می‌داند.
- ثبت‌نام: موبایل + کد ملی.
- API عمومی چت/شماره پیدا نشد.

نتیجه: **نباید فرض کرد شماره‌گیری رینگ عین دیوار است.**

| کار | مسیر صحیح رینگ |
|---|---|
| Discovery | Chromium لاگین‌شده؛ جستجو در DOM / بعداً XHR ضبط‌شده |
| شماره | بعد از لاگین، اگر دکمه تماس شماره داد → `found`؛ اگر فقط چت بود → `chat_only` |
| چت | مسیر اصلی رینگ. ارسال فقط از UI Flutter داخل همان پروفایل |
| استعلام | باز کردن آگهی در Chromium → ورود اگر لازم → چت → یک سؤال → خواندن پاسخ از همان نخ |
| کپی کد دیوار | بی‌فایده است؛ `contact_info_v2` روی رینگ وجود ندارد |

اگر در ضبط زنده مشخص شد بعضی آگهی‌ها اصلاً شماره نمی‌دهند، روتِر برای آن آگهی `chat_only` اجباری است و خروجی اکسل «فقط چت رینگ» جدا می‌شود.

### ۶.۴ الگوریتم انتخاب مسیر (سیستم تصمیم می‌گیرد)

```
function choose_contact(ad, goal):
    # goal: get_phone | inquire_price | marketing_chat

    if ad.platform == "divar":
        if goal == get_phone:
            return api_contact_info_v2
        if goal == inquire_price:
            if chat_available:
                return chromium_click_divar_suggestion("قیمتش چنده؟")
            if phone_found:
                return sms_or_operator_call  # سؤال قیمت؛ قالب بازاریابی نه
        if goal == marketing_chat:
            return semi_auto_draft  # انسان ارسال می‌کند

    if ad.platform == "sheypoor":
        if goal == get_phone:
            return chromium_click("نمایش کامل")
        if goal == inquire_price:
            return chromium_click_chip("قیمت چنده؟")  # چیپ خود سایت
        if goal == marketing_chat:
            return semi_auto_open_chat

    if ad.platform == "ring":
        if not logged_in_ring:
            return need_login
        if goal == get_phone:
            return chromium_open_contact_panel
            # اگر شماره نبود → chat_only
        if goal in (inquire_price, marketing_chat):
            return chromium_ring_chat  # تنها کانال قابل اتکا
```

قانون طلایی: **هدف استعلام ≠ هدف بازاریابی.** قالب تب پیام‌ها برای استعلام استفاده نمی‌شود.

## ۷) لایه L6–L7 — استعلام خودکار قیمت واقعی

خواسته: برای موارد خاص (هزارتومان، توافقی، قیمت نامشخص) سیستم بتواند خودش بپرسد قیمت نقد چیست، بعد تصمیم بگیرد ویژه بشود یا نه.

### ۷.۱ چه چیزهایی استعلام می‌شوند (و چه چیزهایی نه)

استعلام **فقط** اگر:

- `price_kind ∈ {placeholder, negotiable, unknown}`
- یا `hunter_level = suspicious_cheap` بدون واژه معیوب
- و `role = seller`
- و پایش شکارچی روشن است

استعلام **نمی‌شود** اگر:

- معیوب قطعی
- خریدار
- نقد معتبر با confidence بالا (همان را شکار کن)
- پلن/تیک «استعلام خودکار» خاموش است

### ۷.۲ دو سطح اجرا (برای محصول قابل‌فروش هر دو لازم است)

**سطح A — پیش‌فرض تجاری: نیمه‌خودکار هوشمند**

1. سیستم کلاس `inquire` می‌زند، متن/چیپ آماده است.
2. در پنل دکمه «استعلام این مورد» یا صف «استعلام‌های فوری».
3. Chromium همان پروفایل باز می‌شود، چیپ سایت کلیک می‌شود یا متن سؤال Paste.
4. اپراتور Enter می‌زند یا فقط تأیید می‌کند.
5. سیستم بعداً پاسخ را از همان نخ می‌خواند (پولینگ).

ریسک بن پایین. برای اشتراک عمومی همین باید پیش‌فرض باشد.

**سطح B — خودکار محدود (تیک جدا، پیش‌فرض خاموش)**

همان جریان بدون کلیک انسان، با سقف سخت:

| سقف | پیشنهاد |
|---|---|
| استعلام در ساعت / اکانت / پلتفرم | ۸ |
| استعلام در روز / اکانت | ۴۰ |
| فاصله دو استعلام همان اکانت | ≥ ۹۰ ثانیه + jitter |
| یک آگهی | حداکثر یک سؤال |
| متن | فقط قالب استعلام یا چیپ سایت |

اگر پلتفرم محدودیت چت داد → استعلام آن پلتفرم برای آن اکانت می‌ایستد (مثل کپچای شماره). بقیه کار می‌کنند.

ارسال خودکار **قالب بازاریابی** در چت، حتی با این تیک، خاموش می‌ماند. این تیک فقط استعلام است.

### ۷.۳ متن استعلام (سه قالب جدا)

قالب استعلام ≠ قالب تب پیام‌ها.

پیشنهاد فارسی کوتاه (قابل ویرایش):

```
سلام، قیمت نقدی نهایی این «{title}» چقدر است؟ سالمه؟
```

اگر چیپ سایت موجود باشد (شیپور: «قیمت چنده؟» / دیوار: «قیمتش چنده؟») **چیپ مقدم است** — متن سفارشی فرستاده نشود.

رینگ: چیپ اگر در UI بود همان؛ وگرنه همان یک جمله.

### ۷.۴ خواندن پاسخ و تصمیم ویژه (L7)

پولینگ چت همان پروفایل، هر N دقیقه، حداکثر مثلاً ۶ ساعت.

پارس پاسخ فروشنده:

1. استخراج تومان (`parse_toman` + «میلیون/میلیارد»).
2. واژگان معیوب در پاسخ («تعمیره»، «ال‌سی‌دی شکسته»، …).
3. «فروخته شد» / «موجود نیست» → کلاس `gone`.
4. اگر عدد نیامد و معیوب هم نبود → `inquire_timeout` — ویژه نشود.

سپس:

```
اگر معیوب در پاسخ → سطل معیوب، ویژه نه
اگر قیمت نقد معتبر:
     price_kind = cash
     price_toman = عدد پاسخ
     price_source = seller_reply
     برو L3–L4
     اگر خیلی‌مناسب → حالا ویژه + اول صف شماره
اگر timeout → در شیت استعلام بماند، هشدار ویژه نه
```

فقط **بعد از این مرحله** اجازه VIP برای آگهی‌های جای‌نگهدار صادر می‌شود. این همان «سیستم استعلام بگیرد تا بفهمد قیمت واقعی چیست و جزو ویژه بگذارد یا نه» است.

### ۷.۵ مسیر فنی ارسال per-platform (بدون حدس API جعلی)

تا API چت رسمی/پایدار نداریم، ارسال از **همان Chromium لاگین‌شده** است — مثل پازل دیوار که الان هم پروفایل واقعی را می‌راند.

| پلتفرم | عمل استعلام |
|---|---|
| دیوار | باز کردن `/v/{token}` با پروفایل → چت → پیشنهاد «قیمتش چنده؟» یا Paste قالب استعلام |
| شیپور | باز کردن `/v/{slug}-{id}.html` → چت یا چیپ «قیمت چنده؟» |
| رینگ | باز کردن `/a/{id}` در Flutter → چت داخل اپ وب |

خواندن پاسخ: DOM همان پنجره / بعد از ضبط شبکه، XHR چت اگر پایدار بود جایگزین می‌شود. جایگزینی HTTP نباید روز اول اجباری باشد؛ Chromium مسیر صحیح نسخه ۱ است.

---

## ۸) صف‌ها داخل مانیتور (ترتیب کار)

چهار صف جدا، نه یک صف شلوغ:

1. **شکار خیلی‌مناسب بدون شماره** — فوری شماره‌گیری
2. **استعلام باز** — ارسال/خواندن چت استعلام (سقف جدا)
3. **مناسب / VIP بازه دستی**
4. **بقیه سرنخ‌ها**

کپچای یک صف، صف دیگر را اگر اکانت آزاد باشد نگه نمی‌دارد. استعلام از سهمیه شماره جدا شمرده می‌شود (`quota.inquiry` جدید).

## ۹) مدل داده (مهاجرت؛ داده قدیمی دیوار نشکند)

ستون‌های جدید پیشنهادی `leads` (همه با پیش‌فرض امن):

| ستون | معنی |
|---|---|
| `platform` | `divar` / `sheypoor` / `ring` — پیش‌فرض `divar` |
| `native_id` | توکن دیوار / عدد شیپور / id رینگ |
| `role` | seller / buyer |
| `condition` | new / like_new / used / defective / unknown |
| `defect_reason` | متن کوتاه دلیل |
| `price_kind` | cash / negotiable / placeholder / … |
| `price` | تومان اعلامی |
| `price_real` | تومان بعد از استعلام (۰ تا مشخص شود) |
| `price_source` | listing / seller_reply |
| `hunter_level` | none / market / good / steal / suspicious |
| `contact_mode` | phone_and_chat / phone_only / chat_only / … |
| `inquiry_status` | none / queued / sent / awaiting / replied / timeout / skipped |
| `inquiry_reply` | خلاصه پاسخ |
| `classification` | hunt / defective / inquire / suspicious / buyer_drop |

یکتایی: `(platform, native_id)` نه فقط `token`. برای دیوار `token` فعلی همان `native_id` می‌ماند.

## ۱۰) خروجی فایل — تفکیک اجباری

خروجی فعلی فقط دو فیلتر دارد: شماره‌دار / فقط‌چت. برای محصول فروشی کافی نیست.

یک فایل Excel (یا چند CSV با پیشوند تاریخ) با **شیت/فایل جدا**:

| فایل / شیت | فیلتر | ستون‌های اضافه |
|---|---|---|
| `01_شکار_خیلی_مناسب` | hunter_level=steal و غیرمعیوب | پلتفرم، قیمت اعلامی، قیمت واقعی، میانه، درصد، وضعیت کالا |
| `02_شکار_مناسب` | hunter_level=good | همان |
| `03_معیوب` | condition=defective | دلیل معیوب، قیمت (اگر هست) — **جدا از شکار** |
| `04_استعلام_باز` | inquiry awaiting/queued | نوع قیمت (placeholder/توافقی)، وضعیت چت |
| `05_استعلام_پاسخ` | inquiry replied | قیمت واقعی، پاسخ خام، آیا ویژه شد |
| `06_شماره‌دار` | phone found | پلتفرم، شماره، شکار/معیوب/عادی |
| `07_فقط_چت` | chat_only / phone hidden | پلتفرم (دیوار/شیپور/رینگ جدا در ستون) |
| `08_مشکوک` | suspicious | دلیل مشکوک بودن |

ستون مشترک همه شیت‌ها:

`پلتفرم | عنوان | شهر | دسته | قیمت اعلامی | نوع قیمت | قیمت واقعی | وضعیت کالا | سطح شکار | حالت تماس | شماره | وضعیت چت | وضعیت استعلام | لینک | زمان کشف | زمان شماره`

بدون ستون پلتفرم و بدون شیت معیوب/استعلام، مشتری اشتراک نمی‌فهمد چه چیزی را خریده.

پنل سرنخ‌ها هم فیلتر همان سطل‌ها را داشته باشد؛ اکسل فقط خروجی است.

## ۱۱) واکنش‌ها به زبان عملیاتی (چه می‌شود اگر…)

| رویداد | واکنش سیستم |
|---|---|
| عنوان «خریدار…» | حذف از شکار و سرنخ |
| شیپور «وضعیت کالا: معیوب» | سطل معیوب، ویژه نه |
| متن «ال‌سی‌دی شکسته» + قیمت پایین | معیوب حتی اگر فیلد نو گفته باشد (متن بر فیلد می‌چربد اگر قطعی باشد) |
| قیمت `۱٬۰۰۰` | placeholder → استعلام؛ ویژه نه |
| «توافقی» بدون عدد | inquire |
| نقد ۳۳٪ زیر میانه، وضعیت نو | خیلی‌مناسب → تلگرام + اول صف شماره |
| ۴۰٪ زیر میانه بدون معیوب | مشکوک — هشدار نه؛ استعلام سلامت اختیاری |
| دیوار شماره مخفی | contact_mode=chat_only؛ اگر inquire لازم است چت دیوار |
| شیپور بعد از کلیک نمایش کامل، شماره آمد | found |
| رینگ بعد از لاگین فقط چت | chat_only رینگ؛ شماره‌گیری دیوار را صدا نزن |
| پاسخ استعلام «۲۵ میلیون نقد سالمه» | price_real=25M → L4 → اگر شکار شد ویژه |
| پاسخ «تعمیر می‌خواد» | defective؛ ویژه اگر رفته بود پس گرفته شود |
| پاسخ نیامد ۶ ساعت | timeout؛ در شیت استعلام می‌ماند |
| محدودیت چت شیپور | استعلام شیپور آن اکانت می‌ایستد؛ دیوار/رینگ ادامه |
| پلتفرم خاموش در تنظیمات | هیچ کشف/شماره/استعلام آن سایت |

## ۱۲) آنچه در نسخه ۱ پیاده‌سازی می‌شود / نمی‌شود

**نسخه ۱ (قابل فروش):**

- L0–L4 کامل روی دیوار و شیپور (HTML شیپور وضعیت کالا + قیمت)
- روتِر تماس: دیوار API شماره؛ شیپور Chromium «نمایش کامل»؛ رینگ Chromium تماس/چت
- استعلام سطح A (نیمه‌خودکار + چیپ سایت)
- استعلام سطح B با تیک و سقف (اختیاری)
- پارس پاسخ و ارتقا به ویژه
- خروجی ۸ شیت
- سوییچ پلتفرم

**عمداً نسخه ۱ نیست:**

- دستیار مذاکره چنددوری بدون سقف (چت/پیامک بازاریابی خودکار با سقف در `auto-chat-sms-nlu.md` است)
- تشخیص معیوب از روی عکس (بینایی)
- حدس API چت رینگ قبل از ضبط زنده
- یکی‌کردن سهمیه شماره سه سایت

---

## ۱۳) پیش‌فرض با «شروع کن»

1. معیوب ≠ ارزان. سطل جدا، ویژه نه.
2. `۱۰۰۰` و خانواده = جای‌نگهدار = استعلام، ویژه نه تا پاسخ نقد.
3. استعلام با چیپ خود سایت وقتی هست.
4. پیش‌فرض استعلام نیمه‌خودکار؛ خودکار محدود تیک جدا.
5. رینگ چت‌اول؛ کد شماره دیوار روی رینگ اجرا نشود.
6. اکسل تفکیک شکار / معیوب / استعلام / شماره / چت / پلتفرم.

---

## ۱۴) آیا برای مذاکره تخفیف و بررسی کالا به هوش مصنوعی نیاز است؟

**جواب کوتاه (به‌روز با خواست ارسال خودکار):** هسته شکار قاعده‌ای است و به مدل نیاز ندارد. **برای فهمیدن جواب انسان** (چت یا پیامک) مدل زبانی لازم می‌شود — نه برای بستن معامله. جزئیات: `docs/auto-chat-sms-nlu.md` بند ۵.

### ۱۴.۱ سه کار را قاطی نکنید

| کار | ابزار درست | LLM لازم است؟ |
|---|---|---|
| تشخیص معیوب / هزارتومان / خریدار / میانه بازار | قاعده + فیلد سایت + واژگان | خیر — حتی بهتر بدون آن |
| یک سؤال «قیمت نقد چنده؟» | چیپ خود دیوار/شیپور | خیر |
| چند دور چانه برای تخفیف + فهم پاسخ درهم | مدل زبانی می‌تواند پیش‌نویس کند | مفید، اجباری نیست |
| دیدن عکس شکستگی/رنگ‌شدگی خودرو | مدل بینایی | مفید برای پلن بالاتر، نسخه ۱ نه |

اگر شکار را به LLM وابسته کنید: آفلاین نمی‌ماند، هزینه API می‌آید، جواب غیربازیاب می‌شود، و مشتری نمی‌فهمد چرا این آگهی ویژه شد. محصول تجاری شکار باید **قابل توضیح** باشد: «۳۳٪ زیر میانه، وضعیت نو، نقد.»

### ۱۴.۲ مذاکره تخفیف — چرا عامل تمام‌خودکار خطرناک است

فروشنده می‌گوید «بیا پایین‌تر»، «بیعانه بزن»، «کارت به کارت»، «امروز نیا فردا گران‌تره». یک مدل زبانی ممکن است:

- قیمتی قول بدهد که کاربر نمی‌خواهد
- بیعانه را بپذیرد (کلاهبرداری رایج — خود رینگ در FAQ هشدار داده)
- مثل ربات حرف بزند و اکانت را بن کند
- در دیوار/شیپور/رینگ چند پیام پشت‌سرهم بفرستد و محدودیت چت بخورد

مسیر درست محصول پولی:

**دستیار مذاکره (سطح C، پلن بالاتر، پیش‌فرض خاموش)**

1. فقط روی آگهی‌های کلاس شکار یا استعلام.
2. مدل از روی میانه، کفِ کاربر (`max_buy`)، و متن آگهی **۲–۳ پاسخ پیشنهادی** می‌سازد.
3. انسان یکی را می‌فرستد (همان الگوی نیمه‌خودکار فعلی).
4. مدل حق ندارد خودش Send بزند مگر تیک جدا + سقف ۲ پیام اضافه بعد از استعلام.
5. خط قرمز سخت در پرامپت و در کد (هر دو):
   - هیچ بیعانه، کارت، شبا، کد ملی
   - قول ملاقات قطعی ندهد
   - زیر کفِ کاربر نرود
   - اگر فروشنده گفت معیوب است → مذاکره تخفیف شکار را قطع کند، سطل معیوب

هدف دستیار: «۱۰٪ بیار پایین نقد امروز» نه بستن معامله.

بدون LLM هم می‌شود نسخه ۱ را فروخت با **۳ قالب ثابت مذاکره** (قابل ویرایش):

```
نقد امروز {offer} میلیون می‌تونم تسویه کنم. آخرین قیمت‌تون چقدره؟
سالمه، بدون تعمیر؟ اگر آره {offer} نقد.
اگر قیمت روی آگهی تخفیف نقد داره بگید تا هماهنگ کنیم.
```

`offer` = مثلاً میانه − درصد شکار، یا عدد کاربر. این برای موبایل/لپ‌تاپ کافی است. LLM وقتی می‌ارزد که پاسخ‌ها خیلی محاوره‌ای و متنوع باشند.

### ۱۴.۳ بررسی محصول

**متن (نسخه ۱، بدون AI):** همان L1 — فیلد «وضعیت کالا» شیپور + واژگان. این ۸۰٪ موارد معیوب را می‌گیرد.

**عکس (نسخه ۲، اختیاری):** مدل بینایی روی ۲–۳ عکس اول: شکستگی صفحه، آب‌خوردگی، اتاق رنگ خودرو. خروجی فقط برچسب `photo_defect=probable` با اطمینان — ویژه را نگه می‌دارد مگر کاربر بخواهد عکسِ مشکوک را از شکار حذف کند. وابستگی به سرویس ابری؛ روی سیستم مشتری بدون کلید کار نکند.

بررسی فیزیکی (دستگاه را روشن کن، دیاگ بزن) را **هیچ نرم‌افزاری** جایگزین نمی‌شود. محصول باید در هشدار خیلی‌مناسب یک خط بگوید: «قبل از پرداخت حضوری ببینید.»

### ۱۴.۴ جمع‌بندی برای معماری

```
هسته شکار     = قواعد (بدون AI)     ← نسخه ۱، اشتراک اصلی
استعلام قیمت  = چیپ سایت / یک جمله  ← نسخه ۱
دستیار مذاکره = LLM پیش‌نویس + انسان ← پلن بالاتر
بررسی عکس     = Vision اختیاری       ← نسخه ۲
عامل تمام‌خودکار معامله = ساخته نشود
```

نیاز به هوش مصنوعی **برای عرضه اول نیست**. اگر بعداً خواستید «چانه بزن»، آن را دستیار بگذارید نه خلبان خودکار.

تا اعلام شروع، کدی نوشته نمی‌شود.

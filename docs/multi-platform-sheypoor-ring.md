# تحقیق اتصال شیپور و رینگ به مارکتینگ دیوار

> تاریخ: ۱۴۰۵/۰۶/۰۶ (۲۰۲۶-۰۸-۲۸)
> وضعیت: **فقط تحقیق** — تا تأیید کارفرما کدنویسی شروع نمی‌شود
> نسخه فعلی برنامه: ۲.۱.۲۵ (فقط دیوار)

---

## ۱) خلاصه اجرایی

سؤال: آیا می‌شود همان قابلیت‌های دیوار (جستجو با دسته/شهر/کلمه، بازه قیمت، هشدار ویژه، گرفتن شماره، چت نیمه‌خودکار، چنداکانت Chromium) را روی **شیپور** و **رینگ** هم داشت، با **یک پروفایل اکانت** که در هر سه سایت لاگین شود و **کد پیامک هر پلتفرم جدا** وارد گردد؟

| قابلیت | دیوار (الان) | شیپور | رینگ |
|---|---|---|---|
| جستجوی عمومی بدون لاگین (دسته + شهر + کلمه) | ✅ HTML `/s/{شهر}/{دسته}?q=` | ✅ HTML `/s/{شهر}/{دسته}?q=` — زنده تأیید شد | ⚠️ وب Flutter است؛ لیست عمومی در HTML تقریباً خالی است |
| قیمت روی لیست آگهی | ✅ | ✅ تومان روی کارت آگهی | ⚠️ بعد از باز شدن جزئیات / اپ |
| بازه قیمت + هشدار VIP | ✅ فیلتر محلی | ✅ همان روش (قیمت از HTML) | ✅ بعد از استخراج قیمت |
| لاگین با شماره + OTP | ✅ `divar.ir/user` + JWT v5 | ✅ `sheypoor.com/session` شماره موبایل | ✅ مودال «ورود یا ثبت نام» + کد ۶ رقمی |
| شماره تماس | لاگین + `contact_info_v2` | لاگین + «نمایش کامل» (روی صفحه `0912XXX…`) | لاگین لازم: «برای گرفتن اطلاعات تماس ابتدا وارد شوید» |
| چت | نیمه‌خودکار | دکمه «چت» روی آگهی | چت مستقیم داخل اپ/سایت |
| API رسمی توسعه‌دهنده | کنار دیوار (سردپیام ندارد) | ❌ پیدا نشد | ❌ پیدا نشد |
| پروفایل Chromium پایدار | ✅ الان | ✅ همان پوشه — کوکی دامنه جدا | ✅ همان پوشه — کوکی دامنه جدا |

**نتیجه:** اتصال هر دو پلتفرم **شدنی است** و با معماری فعلی سازگار است، به شرط اینکه:

1. دیوار/شیپور/رینگ پشت یک **آداپتور پلتفرم** بروند (نه کپی سه‌بارهٔ `client.py`).
2. **یک پروفایل Chromium** برای هر اکانت بماند؛ لاگین سه سایت داخل همان پنجره/همان `user-data-dir`.
3. OTP هر سایت **جدا** باشد (سه پیامک جدا — دیوار، شیپور، رینگ).
4. برای رینگ، کشف لیست/شماره در فاز اول بیشتر از **همان Chromium لاگین‌شده** باشد تا API مخفی Flutter (اندپوینت رسمی عمومی نیست).

هیچ‌کدام API رسمی «جستجوی آزاد + شماره آگهی دیگران» ندارند. مسیر درست همان مسیر فعلی دیوار است: خواندن عمومی + لاگین انسانی برای شماره + چت نیمه‌خودکار.

## ۲) شیپور (`sheypoor.com`)

منبع زنده ۱۴۰۵/۰۶/۰۶ (صفحات عمومی سایت، نه حدس).

### ۲.۱ هویت محصول

- بازار آگهی ایران، رقیب مستقیم دیوار (املاک، خودرو، موبایل، استخدام، خدمات، …).
- وب: Next.js (`_next/static`).
- اپ: `com.sheypoor.mobile`.
- ورود: شماره موبایل، بدون ایمیل.

### ۲.۲ آدرس‌های عمومی (مشابه دیوار)

| کار | دیوار | شیپور (زنده) |
|---|---|---|
| لیست دسته | `divar.ir/s/{شهر}/{دسته}` | `sheypoor.com/s/{شهر}/{دسته}` |
| جستجوی کلمه | `?q=` | `?q=` — نمونه: `/s/tehran/car?q=پراید` عنوان صفحه: «نتایج جستجو برای پراید» |
| صفحه آگهی | `/v/{slug}/{token}` | `/v/{slug}-{id}.html` — نمونه: `/v/samsung-level-u2-466163319.html` |
| شناسه آگهی | توکن کوتاه حروفی | عدد ۹ رقمی در انتهای URL (مثلاً `466163319`) |
| لاگین | `/user` | `/session` — «ورود / ثبت نام» + فیلد شماره موبایل |
| صفحه‌بندی | `page=` | `page_num=` (در `robots.txt` صریحاً Allow شده) |

`robots.txt` شیپور:

```
Disallow: /session
Disallow: /search
Disallow: /*?
Allow: /*page_num=
```

یعنی مسیر HTML دسته (`/s/...`) برای خزش باز است؛ لاگین و بعضی queryها را رسمی نمی‌خواهند. برنامه مثل دیوار از HTML عمومی لیست استفاده می‌کند.

### ۲.۳ دسته‌های اصلی شیپور (اسلاگ زنده)

گروه:

- `vehicles` وسایل نقلیه → `car`, `commercial-cars`, `motorcycles`, `classic-cars`, `agriculture-construction`
- `real-estate` املاک → `houses-apartments-for-sale`, `house-apartment-for-rent`, `villa-for-sale`, …
- `jobs` استخدام
- `services` خدمات
- `home` لوازم خانگی
- `electronics` لوازم الکترونیکی → `laptop-computer`, `audio-video`, `photography`, `video-games-consoles`, …
- `mobile-tablet-accessories` موبایل و تبلت → `mobile-tablet`, `mobile-accessories`, `sim-card`
- `industrial-commercial` صنعتی
- `personal-stuff` لوازم شخصی
- `sports-games-hobbies` ورزش و فراغت

شهر: همان الگوی دیوار (`tehran`, `karaj`, `mashhad`, `isfahan`, `sari`, `amol`, `iran`, …). جدول شهر فعلی برنامه قابل استفاده است؛ چند اسلاگ شیپور ممکن است با دیوار فرق کند و در پیاده‌سازی با جدول نگاشت پر می‌شود.

### ۲.۴ قیمت و شکار VIP

روی کارت لیست، قیمت تومان آمده (مثلاً `۴۴۰,۰۰۰,۰۰۰` یا «قیمت توافقی»).  
بازه قیمت مثل دیوار **محلی** اعمال می‌شود: اگر قیمت خوانده شد و داخل بازه نبود، سرنخ ذخیره نمی‌شود. «قیمت توافقی» اگر بازه فعال باشد رد می‌شود (همان سیاست فعلی دیوار).

هشدار ویژه (VIP) روی همان پایش کار می‌کند: آگهی منطبق شیپور هم تلگرام/بله/روبیکا می‌گیرد، با برچسب پلتفرم.

### ۲.۵ شماره تماس

صفحه آگهی بدون لاگین شماره را **ماسک** می‌کند:

`0912XXX4776 (نمایش کامل)`

دکمه‌های پایین صفحه: **اطلاعات تماس** و **چت**.

نتیجه عملی:

- Discovery بدون لاگین شدنی است.
- شماره کامل مثل دیوار نیاز به سشن لاگین‌شده دارد.
- بعضی آگهی‌ها فقط چت خواهند بود.
- API داخلی شماره در این محیط TLS بسته شد؛ روی IP ایران باید با همان پروفایل Chromium یا XHR سایت کشف شود (احتمالاً چیزی شبیه `/api/.../listings/{id}/phone` بعد از کوکی سشن). تا آن کشف، مسیر قابل اتکا: باز کردن آگهی در همان پروفایل و خواندن شماره بعد از «نمایش کامل».

### ۲.۶ لاگین

صفحه `https://www.sheypoor.com/session`:

1. شماره موبایل
2. ارسال کد
3. ورود / ثبت‌نام یکسان است

کد OTP شیپور **جدا از دیوار** است (دو پیامک جدا).

کوکی دامنه `.sheypoor.com` داخل همان پروفایل Chromium اکانت ذخیره می‌شود؛ تزریق جعلی لازم نیست.

## ۳) رینگ (`ring.ir`)

منبع: سایت، FAQ، صفحه آگهی `/a/...`، اخبار راه‌اندازی ۱۴۰۵، اپ `com.ads.ring`.

### ۳.۱ هویت محصول

- پلتفرم آگهی ایرانی جدید، رقیب دیوار/شیپور.
- شرکت: «همراه نیاز ایرانیان».
- دسته‌ها: املاک، وسایل نقلیه، خدمات، خانه، سرگرمی، استخدام، دیجیتال، لوازم فردی، صنعتی، اجتماعی.
- ثبت‌نام: شماره موبایل (+ در اپ تطبیق کد ملی).
- ورود: **فقط OTP** (FAQ: «ورود تنها با رمز یک‌بارمصرف»).
- آگهی ۳۰ روزه؛ چت مستقیم خریدار/فروشنده.

### ۳.۲ شکل فنی وب

- صفحه اصلی و جزئیات آگهی **Flutter Web** هستند (متن «flutter typography measurement» در HTML).
- HTML عمومی تقریباً خالی است — برخلاف دیوار و شیپور.
- آگهی: `https://ring.ir/a/{id}` مثلاً `https://ring.ir/a/31eCoJ234EhA`.

از متن استخراج‌شدهٔ همان صفحه آگهی (زنده):

- «ورود یا ثبت نام»
- «برای گرفتن اطلاعات تماس کاربر ابتدا وارد شوید»
- «شماره موبایل خود را وارد کنید»
- «کد تایید ۶ رقمی ارسال شده به شماره همراه خود را وارد کنید»
- پس از ورود: «اطلاعات تماس / تماس تلفنی: 0912 …»

پس مدل تماس **عین دیوار** است: جستجو/جزئیات عمومی، شماره پشت لاگین.

### ۳.۳ جستجو

جستجو بر اساس شهر، دسته، قیمت در اپ و وب هست، ولی به‌خاطر Flutter، **اسکریپ HTML لیست مثل دیوار جواب پایدار نمی‌دهد**.

مسیر پیشنهادی (ترتیب اولویت):

1. **پروفایل Chromium همان اکانت** → باز کردن رینگ → جستجوی دسته/کلمه در DOM → برداشت لینک `/a/{id}` + عنوان + قیمت.
2. بعد از اجرای زنده روی IP ایران: ضبط درخواست شبکه Flutter (احتمالاً `api.*ring*` یا gateway داخلی) و اگر پایدار بود، کلاینت HTTP مثل `DivarClient` اضافه شود.
3. تا ضبط شبکه، مانیتور رینگ از مسیر Chromium (کم‌حجم، با همان RateLimiter) کار می‌کند — نه اسکرپ کورکورانه کل سایت.

### ۳.۴ لاگین و پروفایل

با خواسته «پروفایل عوض نشود» کاملاً جور است:

- همان `accounts/<name>/chromium`
- دامنه سوم: `ring.ir`
- کاربر در همان پنجره وارد رینگ می‌شود، کد ۶ رقمی **رینگ** را می‌زند، ذخیره پروفایل کوکی رینگ را هم برمی‌دارد.

API OTP جدا (مثل v5 دیوار) برای رینگ در این تحقیق پیدا نشد؛ مسیر اول همان مرورگر است.

## ۴) مدل اکانت سه‌پلتفرمه (بدون عوض کردن ایده پروفایل)

خواسته‌ها:

- یک حساب در پنل = یک پروفایل Chromium
- در هر سه سایت ثبت/لاگین شود
- کد هر کدام جدا وارد شود
- تب اکانت‌ها ظاهرش عوض اساسی نشود

### ۴.۱ آنچه روی دیسک می‌ماند

```
accounts/<name>/
  account.json          # نام، شماره، وضعیت
  chromium/             # یک user-data-dir — کوکی divar.ir + sheypoor.com + ring.ir
  session.json          # JWT دیوار (شماره‌گیری API)
  sheypoor.json         # در صورت کشف توکن API شیپور (اختیاری)
  ring.json             # در صورت کشف توکن API رینگ (اختیاری)
```

Chromium از قبل کوکی را **per-domain** نگه می‌دارد. سه لاگین در یک پروفایل تداخل ندارند.

### ۴.۲ جریان پیشنهادی UI (حداقلی)

الان: «افزودن پروفایل» → Chromium روی `divar.ir/user`.

بعد از تأیید:

1. همان دکمه، همان کارت اکانت.
2. Chromium همان پروفایل را باز می‌کند با **سه تب** (یا یک صف راهنما):
   - دیوار: `https://divar.ir/user`
   - شیپور: `https://www.sheypoor.com/session`
   - رینگ: `https://ring.ir/` (مودال ورود)
3. کاربر با **همان شماره** وارد می‌شود؛ **سه SMS جدا** می‌آید؛ هر کد را در تب همان سایت می‌زند.
4. «ذخیره پروفایل» مثل الان کوکی همان پنجره را می‌خواند — این بار برای هر سه دامنه.
5. وضعیت روی کارت (بدون شلوغ‌کردن تب):
   - دیوار: ذخیره شده / نیاز به لاگین
   - شیپور: ذخیره شده / نیاز به لاگین
   - رینگ: ذخیره شده / نیاز به لاگین

OTP اختیاری API دیوار سر جایش می‌ماند. برای شیپور/رینگ تا کشف API، OTP داخل همان Chromium است (دقیقاً مطابق «پروفایل لازم به تغییر خاصی نیست»).

اگر یکی از سه سایت لاگین نشود، اسکن آن پلتفرم برای آن اکانت خاموش می‌شود؛ بقیه کار می‌کنند (مثل کپچای یک اکانت دیوار).

## ۵) معماری موتور (بعد از تأیید)

الان همه چیز به `DivarClient` چسبیده است. برای سه سایت نباید `client.py` را سه بار کپی کرد.

```
Platform (قرارداد واحد)
  search(keyword, city, category, page) -> [Post]
  get_post(token) -> detail
  get_phone(token, session) -> found|hidden|error
  login_url / home_url
  cookie_domains

DivarPlatform      ← کد فعلی client.py پشت این می‌رود
SheypoorPlatform   ← HTML /s/... + جزئیات /v/...-{id}.html + شماره بعد از سشن
RingPlatform       ← Chromium/DOM یا API بعد از ضبط زنده
```

مانیتور فعلی:

```
Watcher  →  برای هر پایش فعال، هر پلتفرم تیک‌خورده را search می‌کند
Worker   →  صف شماره را با اکانت دارای سشن همان پلتفرم خالی می‌کند
```

کلید یکتای سرنخ در دیتابیس باید بشود:

`platform + native_id`  
مثال: `divar:AbCdE` / `sheypoor:466163319` / `ring:31eCoJ234EhA`

ستون‌های لازم (مهاجرت SQLite، داده قدیمی دیوار دست نمی‌خورد):

- `leads.platform` پیش‌فرض `'divar'`
- `leads.native_id`
- یکتایی روی `(platform, native_id)` نه فقط `token`

پایش (کلمات کلیدی):

- همان فرم فعلی: دسته، شهر، کلمه، قیمت از–تا، VIP
- تیک اختیاری: دیوار / شیپور / رینگ (پیش‌فرض هر سه روشن)
- شکار قیمت: یک کالا + بازه → هر سه سایت؛ اولین منطبق VIP همان کانال‌های فعلی

ضدبلاک:

- RateLimiter جدا per-platform (سهمیه شماره دیوار را با شیپور قاطی نکنیم)
- سقف روزانه جدا یا سقف کلی IP قابل تنظیم
- کپچا/محدودیت یک سایت بقیه را نگه نمی‌دارد

چت:

- مثل دیوار نیمه‌خودکار می‌ماند (قالب + باز کردن آگهی در همان پروفایل)
- ارسال انبوه خودکار در هیچ‌کدام اضافه نمی‌شود

## ۶) نقشه قابلیت‌ها نسبت به پنل فعلی

| بخش پنل | تغییر |
|---|---|
| داشبورد | KPI می‌تواند تفکیک دیوار/شیپور/رینگ داشته باشد؛ اسکن همان دکمه‌ها |
| اکانت‌ها | ظاهر تقریباً همان؛ ذخیره پروفایل سه دامنه؛ سه وضعیت لاگین کوچک |
| کلمات | تیک پلتفرم + همان دسته/شهر/قیمت/VIP |
| پیام‌ها | قالب مشترک؛ لینک آگهی پلتفرم درست باز می‌شود |
| سرنخ‌ها | ستون/برچسب پلتفرم؛ فیلتر دیوار/شیپور/رینگ |
| تنظیمات | سهمیه per-platform (پیش‌فرض محافظه‌کارانه) |
| لاگ | پیشوند `[divar]` `[sheypoor]` `[ring]` |

شکار قیمت (VIP): همان منطق `consider_new_lead` + `pricing.in_range` روی هر سه منبع.

## ۷) ریسک‌ها

| ریسک | سطح | برخورد |
|---|---|---|
| API غیررسمی شیپور/رینگ عوض شود | متوسط | آداپتور جدا + HTML/Chromium پشتیبان |
| رینگ فقط Flutter | متوسط | فاز ۱ Chromium؛ فاز ۲ ضبط شبکه روی IP ایران |
| سه OTP روی یک شماره در دقیقه | متوسط | ویزارد ترتیبی (اول دیوار، بعد شیپور، بعد رینگ) تا پیامک قاطی نشود |
| بلاک IP اگر هر سه را سریع بزنیم | بالا اگر بی‌ملاحظه | تأخیر جدا، سقف جدا، یک Worker آرام |
| حجم آگهی سه‌برابر | متوسط | صف مشترک با اولویت VIP سپس جدیدترین |
| TLS این محیط به شیپور/رینگ handshake نداد | — | مثل دیوار؛ تست زنده فقط روی سیستم ایران |
| حقوقی/اسپم | متوسط | همان سیاست فعلی: چت انسانی، پیامک رسمی ملی‌پیامک، بدون ارسال خودکار چت |

## ۸) آنچه عمداً در فاز اول **نمی‌شود**

- حل خودکار کپچا/پازل هیچ سایتی
- ارسال خودکار چت در شیپور یا رینگ
- سه پروفایل Chromium جدا برای سه سایت (خلاف خواسته)
- وابستگی به API رسمی که وجود ندارد
- حدس زدن اندپوینت شماره رینگ قبل از ضبط زنده

## ۹) ترتیب پیاده‌سازی پیشنهادی (بعد از «شروع کن»)

1. قرارداد `Platform` + انتقال دیوار فعلی پشت آن (رفتار دیوار نباید بشکند).
2. ستون `platform` در دیتابیس + تست مهاجرت.
3. شیپور: جستجوی HTML + پارس `/v/...-{id}.html` + قیمت + تطبیق کلمه/بازه/VIP.
4. پروفایل: باز شدن سه تب لاگین + ذخیره کوکی سه دامنه + نشان وضعیت.
5. شیپور: گرفتن شماره با سشن (Chromium یا API بعد از کشف زنده).
6. رینگ: برداشت آگهی از Chromium لاگین‌شده + شماره بعد از ورود.
7. مانیتور سه‌منبع + برچسب پلتفرم در سرنخ/تلگرام/اکسل.
8. تست آفلاین با mock شیپور/رینگ (مثل `mock_divar.py`).

تخمین حجم: متوسط رو به بالا؛ هسته دیوار بازنویسی کامل نمی‌شود، فقط پشت اینترفیس می‌رود.

## ۱۰) تأییدهای لازم قبل از کد

لطفاً قبل از شروع کدنویسی این‌ها را مشخص کنید (پیشنهاد پیش‌فرض داخل پرانتز):

1. هر پایش روی **هر سه سایت** باشد مگر تیک خاموش شود؟ (**بله**)
2. پروفایل: سه تب در **همان** Chromium، بدون ویزارد پیچیده OTP در پنل؟ (**بله — کد داخل خود سایت**)
3. اگر شیپور یا رینگ لاگین نباشد، اسکن همان سایت برای آن اکانت رد شود نه کل مانیتور؟ (**بله**)
4. سقف شماره جدا per-platform؟ (**بله، پیش‌فرض مثل دیوار ۶۰**)
5. نام محصول و تب‌ها همان «مارکتینگ دیوار» بماند؟ (**بله**)

پس از اعلام شروع، پیاده‌سازی از بند ۹ همین سند انجام می‌شود.

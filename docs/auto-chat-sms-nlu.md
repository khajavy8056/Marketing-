> وضعیت: **فقط مستند** — تا تأیید، کدنویسی شروع نمی‌شود
> وابسته: `docs/intelligence-contact-export.md` · `docs/multi-platform-sheypoor-ring.md`

## ۰) اصلاح نسبت به نسخه ۲.۱.۲۵ و مستندهای قبلی

در کد فعلی (`messaging.py`، تب پیام‌ها، `diag.py`):

| کانال | ۲.۱.۲۵ واقعاً چه می‌کند |
|---|---|
| پیامک | **خودکار** اگر تیک «ارسال خودکار» روشن باشد — ملی‌پیامک، سقف روزانه |
| چت دیوار | **نیمه‌خودکار** — قالب آماده + انسان Paste می‌کند |

خواست شما از این به بعد (و مبنای پیاده‌سازی بعدی):

> چت مثل پیامک **کاملاً خودکار** است. قالب ذخیره‌شده، اگر فعال باشد، با سقف‌های تعریف‌شده به هر آگهی **فقط‌چت** فرستاده می‌شود. همین باید روی شیپور و رینگ هم باشد. آگهی شماره‌دار پیامک خودکار می‌گیرد. اگر پاسخ آمد (چت یا پیامک) باید خوانده و فهمیده شود. برای ویژه، استعلام قیمت از همان کانال می‌رود و روی جواب عکس‌العمل مناسب می‌شود. هوش مصنوعی برای **درک زبان انسان در پاسخ** است، نه برای بستن معامله.

مستندهای قبلی که «چت نیمه‌خودکار سیاست محصول است» را برای محصول بعدی **باطل** می‌کنند. نیمه‌خودکار فقط توصیف کد امروز است.

## ۱) دو موتور خروجی، یک موتور ورودی

```
آگهی منطبق
    │
    ├─ شماره پیدا شد ──► موتور پیامک (ملی‌پیامک)  ──► قالب sms
    └─ فقط چت / شماره مخفی ──► موتور چت (per-platform) ──► قالب chat
                                    │
ویژه/شکار نیازمند قیمت ──► همان کانال، قالب inquire (جدا)
                                    │
                          صندوق پاسخ (چت + پیامک)
                                    │
                          تحلیلگر پاسخ (قاعده + NLU)
                                    │
                          عمل: ویژه / معیوب / فروخته / ادامه / توقف
```

سه قالب جدا در تنظیمات (قاقی نشوند):

| کلید | کی می‌رود | مثال |
|---|---|---|
| `tpl_chat` | فقط‌چت، تیک چت خودکار روشن | قالب فعلی تب پیام‌ها |
| `tpl_sms` | شماره‌دار، تیک پیامک خودکار روشن | قالب فعلی پیامک |
| `tpl_inquire` | فقط کلاس استعلام/ویژه بدون قیمت نقد | «قیمت نقدی نهایی «{title}» چقدر است؟ سالمه؟» |

چیپ خود سایت («قیمت چنده؟») برای استعلام مقدم بر `tpl_inquire` است اگر روی صفحه باشد.

## ۲) موتور چت خودکار — سه پلتفرم

API رسمی سردپیام در هیچ‌کدام برای آگهی دیگران وجود ندارد (کنار دیوار فقط Opt-in). مسیر صحیح نسخه ۱ برای **هر سه**: همان پروفایل Chromium لاگین‌شده — مثل پازل دیوار که الان هم همان پنجره را می‌راند.

### ۲.۱ دیوار

1. Worker چت یک سرنخ `phone_status=hidden` برمی‌دارد.
2. پروفایل اکانت آماده را باز می‌کند روی `/v/{token}`.
3. دکمه چت → فیلد پیام → Paste قالب شخصی‌سازی‌شده (`{title}`) → ارسال.
4. اگر پیشنهاد هوشمند دیوار روی صفحه بود، برای **استعلام** همان چیپ؛ برای **بازاریابی** قالب ذخیره.
5. `chat_status=sent` + زمان. یک آگهی یک‌بار مگر کاربر «ارسال مجدد» بزند.
6. محدودیت چت/کپچا → همان اکانت برای چت دیوار می‌ایستد؛ پیامک و پلتفرم‌های دیگر ادامه.

اگر بعداً XHR `chat.divar.ir` پایدار ضبط شد، می‌تواند جایگزین Chromium شود؛ روز اول اجباری نیست.

### ۲.۲ شیپور

1. همان پروفایل، دامنه `sheypoor.com` لاگین.
2. `/v/{slug}-{id}.html` → «چت با {نام}».
3. قالب `tpl_chat` یا برای استعلام چیپ «قیمت چنده؟».
4. محدودیت جدا از دیوار.

### ۲.۳ رینگ (متفاوت، چت‌اول)

خیلی از آگهی‌های رینگ ممکن است اصلاً شماره ندهند. پس موتور چت رینگ **مسیر اصلی تماس** است نه فرعی.

1. پروفایل، `ring.ir` لاگین (OTP رینگ).
2. `/a/{id}` در Flutter → چت.
3. ارسال قالب. خواندن پاسخ از همان نخ UI.
4. کد `contact_info_v2` دیوار اینجا صدا زده نمی‌شود.

### ۲.۴ تیک و سقف (مثل پیامک)

تنظیمات جدید، کنار تیک پیامک:

- `chat_auto_on` — پیش‌فرض خاموش تا کاربر آگاهانه روشن کند (مثل `sms_auto_on_new`)
- سقف در ساعت / اکانت / پلتفرم (پیشنهاد ۸)
- سقف روزانه / اکانت (پیشنهاد ۴۰)
- فاصله دو ارسال ≥ ۹۰ ثانیه + jitter
- سقف کل IP چت جدا از سقف شماره

اگر قالب خالی باشد موتور چت روشن نمی‌شود (پیام واضح).

شخصی‌سازی `{title}` اجباری است تا متن صددرصد یکسان نباشد.

## ۳) موتور پیامک — همان هسته فعلی + ورودی

خروجی: بدون تغییر معماری — `maybe_send_for_lead` وقتی شماره `found` شد.

ورودی پاسخ پیامک (الان در کد نیست، برای ویژه و تحلیل لازم است):

ملی‌پیامک: دریافت برای مشتری رایگان است؛ وب‌سرویس Receive (SOAP `GetMessages`) و «انتقال ترافیک» (وب‌هوک GET).

این برنامه **محلی روی ویندوز** است؛ وب‌هوک عمومی ندارد. مسیر درست: **پولینگ صندوق** هر ۱–۲ دقیقه با همان نام کاربری/رمز:

- پیام‌های خوانده‌نشده
- تطبیق `from` با `leads.phone`
- ذخیره متن، علامت خوانده‌شده
- دادن به تحلیلگر

اگر خط اختصاصی قابلیت دریافت نداشته باشد، در تنظیمات نوشته شود: «پاسخ پیامک روی این خط نمی‌آید — پاسخ را از چت بخوان» و استعلام ویژه برای شماره‌دارها ترجیح چت داشته باشد اگر چت هم موجود است.

## ۴) صندوق پاسخ و تطبیق

جدول `replies`:

| فیلد | معنی |
|---|---|
| platform | divar / sheypoor / ring / sms |
| native_id / phone | کلید تطبیق |
| direction | in |
| body | متن خام |
| received_at | زمان |
| nlu_intent | خروجی تحلیل |
| nlu_confidence | 0–1 |
| acted | آیا روی سرنخ اعمال شد |

تطبیق چت: همان آگهی/نخ.  
تطبیق پیامک: شماره نرمال‌شده `09…`. اگر یک شماره چند آگهی دارد → جدیدترین سرنخ همان شماره که `sms_status=sent` یا `inquiry_status=sent`.

پولینگ:

- چت: دوره‌ای باز کردن صندوق/نخ‌های اخیر در Chromium همان پروفایل (یا XHR بعد از ضبط)
- پیامک: GetMessages ملی‌پیامک

## ۵) تحلیلگر پاسخ — اینجا هوش مصنوعی لازم است

سؤال شما: AI برای درک متن انسان در جواب، نه برای خلبان معامله.

دو لایه. لایه قاعده **همیشه** اول می‌آید (آفلاین، رایگان، قابل توضیح). مدل فقط وقتی قاعده کم‌اطمینان است.

### ۵.۱ لایه قاعده (بدون مدل)

از متن نرمال‌شده:

| نشانه | intent پیشنهادی | اطمینان |
|---|---|---|
| عدد تومان/میلیون/میلیارد قابل پارس | `price_quote` | بالا اگر یک عدد واضح |
| معیوب، تعمیره، شکسته، اوراقی، … | `defect_admit` | بالا |
| فروخته، رفت، موجود نیست، کنسل | `gone` | بالا |
| بیعانه، کارت به کارت اول، شبا بده | `scam_deposit` | بالا |
| بله، موجوده، هست هنوز | `available_yes` | متوسط |
| نه، نمی‌دم، تخفیف نداره | `refuse_discount` | متوسط |
| سلام، خوبی، در خدمتم (بدون عدد) | `greeting` | متوسط — هنوز قیمت نیست |

اگر دو نشانه متناقض (عدد + معیوب) → هر دو اسلات پر می‌شود: قیمت و معیوب.

### ۵.۲ لایه NLU (مدل زبانی) — وقتی لازم است

مواردی که قاعده کم می‌آورد، دقیقاً زبان انسان:

- «بیست و پنج تموم نقدی اگه تا ظهر بیای وگرنه فردا بیست و هشت»
- «یه ترک ریز گوشه ال‌سی‌دی داره ولی روی کارکردش اثر نداره»
- «قیمت روی آگهی پایه‌ست بیا پایین حرف می‌زنیم»
- «همون زدم دیگه برادر»

خروجی اجباری ساخت‌یافته (JSON)، نه مقاله:

```
intent: price_quote | defect_admit | gone | negotiate | scam_deposit
        | available_yes | available_no | refuse_discount | question | unclear
slots:
  price_toman: int | null
  price_kind: cash | installment | negotiable | null
  condition: new | used | defective | unknown
  deadline: text | null
  wants_deposit: bool
confidence: 0–1
summary_fa: یک خط
```

**کلید API ابری لازم نیست.** درک متن با مدل **داخل خود نصب** انجام می‌شود (بند ۵.۴). اگر فایل مدل هنوز دانلود نشده باشد فقط لایه قاعده کار می‌کند.

فقط متن همان پاسخ به مدل محلی می‌رود. پرامپت خط قرمز دارد: بیعانه را `scam_deposit` کن؛ قول معامله نساز.

مدل **پیام بعدی را خودش ارسال نمی‌کند** مگر همان سقف استعلام (یک سؤال). برای بازاریابی، پاسخ فقط ثبت و به اپراتور/هشدار می‌رود.

### ۵.۴ مدل محلی همراه برنامه (بدون هزینه API)

بله — برای همین محصول درست است و با نصب فعلی جور است (الان هم Chromium جدا دانلود می‌شود، داخل گیت نیست).

کار ما **چت آزاد نیست**؛ طبقه‌بندی جواب کوتاه فارسی است (یک تا پنج خط). مدل ۷۰ میلیاردی لازم نیست.

| گزینه | حجم تقریبی روی دیسک | RAM | سرعت CPU لپ‌تاپ معمولی | فارسی | حکم |
|---|---|---|---|---|---|
| فقط قاعده | ۰ | ۰ | فوری | واژگان | همیشه روشن |
| **Qwen2.5-1.5B Instruct Q4_K_M** | ~۱٫۱–۱٫۵ GB | ~۲ GB | حدود ۱–۳ ثانیه هر پاسخ | خوب (چندزبانه) | **پیشنهاد پیش‌فرض نصب** |
| Qwen2.5-3B Instruct Q4_K_M | ~۲–۲٫۵ GB | ~۳٫۵ GB | ۲–۶ ثانیه | بهتر | اگر RAM ≥ ۱۶ GB |
| Llama 3.2 1B | ~۱ GB | ~۱٫۵ GB | سریع | فارسی ضعیف‌تر | نه برای این کار |
| مدل ۷B به بالا | ۴ GB+ | ۸ GB+ | کند روی CPU | بهتر | داخل نصب‌کننده نیاید |

لایسنس Qwen 2.5 معمولاً Apache-2.0 است — برای فروش برنامه مناسب‌تر از مدل‌های محدود متا است. فایل GGUF داخل مخزن گیت **نمی‌آید**؛ مثل Chromium موقع نصب یا «اولین استعلام» از آینه دانلود می‌شود به:

`%LOCALAPPDATA%\DivarMarketing\nlu-model\`

موتور اجرا: `llama.cpp` (فایل `llama-cli.exe` / بایندینگ پایتون). GPU لازم نیست؛ AVX2 روی CPU ویندوز ۱۰ کافی است. کانتکست کوتاه (۵۱۲ توکن) چون پاسخ پیامک/چت کوتاه است.

جریان:

```
پاسخ آمد
  → لایه قاعده
  → اگر اطمینان بالا: همان عمل
  → اگر مبهم و فایل مدل موجود: Qwen محلی → JSON intent/slots
  → اگر مدل نبود: «نیاز به خواندن» در پنل؛ شکار و ارسال قطع نمی‌شود
```

نصب‌کننده تیک اختیاری می‌گیرد: «دانلود موتور درک متن (~۱٫۵ GB، یک‌بار، بدون اینترنت بعدی)». بدون تیک هم برنامه کامل کار می‌کند؛ فقط جواب‌های محاوره‌ای را انسان می‌خواند.

Ollama جدا نصب‌کردن روی سیستم مشتری اجباری نیست — وابستگی اضافه و گیج‌کننده است. موتور داخل پوشه برنامه بماند.

هزینه API ماهانه: صفر. هزینه یک‌بار: حجم دانلود روی اینترنت مشتری، مثل Chromium.

### ۵.۳ عکس‌العمل بعد از تحلیل

زمینه = چرا پیام رفته بود: `marketing` یا `inquire`.

**اگر inquire (ویژه/شکار):**

| intent | عمل |
|---|---|
| `price_quote` نقد | `price_real` ← عدد → L3–L4 شکار → خیلی‌مناسب شود یا نشود |
| `defect_admit` | سطل معیوب؛ ویژه پس گرفته شود |
| `gone` | `removed`؛ هشدار نه |
| `scam_deposit` | مشکوک؛ ویژه نه؛ به کاربر هشدار کلاهبرداری |
| `negotiate` بدون عدد | در شیت استعلام بماند؛ یک پیام پیشنهاد تخفیف **نفرست** مگر تیک دستیار |
| `unclear` / کم‌اطمینان | به اپراتور در پنل «نیاز به خواندن» |
| `greeting` | صبر دور بعد؛ هنوز قیمت نیست |

**اگر marketing (قالب چت/پیامک کسب‌وکار):**

| intent | عمل |
|---|---|
| پاسخ هرچه بود | `lead_status=replied`؛ متن در سرنخ |
| `gone` | بستن |
| `scam_deposit` | هشدار |
| سؤال برگشتی | نوتیف برای انسان — ربات بازاریابی جواب آزاد نمی‌دهد |

هدف AI این‌جا **فهمیدن** است تا ویژه غلط ساخته نشود و سرنخ «پاسخ داد» از «سکوت» جدا شود.

## ۶) ویژه + استعلام روی همان کانال‌ها

جریان شکار وقتی قیمت نقد نیست:

```
کلاس inquire
  → اگر شماره هست و پیامک خودکار/استعلام روشن: tpl_inquire از ملی‌پیامک
  → وگرنه اگر چت هست: چت خودکار tpl_inquire یا چیپ سایت
  → inquiry_status=sent
  → صندوق پاسخ → تحلیلگر
  → عمل بخش ۵.۳
```

اولویت کانال استعلام:

1. چت اگر موجود است (چیپ سایت، ارزان‌تر از پیامک، پاسخ داخل همان اپ)
2. پیامک اگر فقط شماره است
3. هر دو نرو مگر تیک «هر دو کانال» — اسپم دوگانه حساب را می‌سوزاند

سقف استعلام از سقف بازاریابی **جدا** است تا شکار، سهمیه پیام تبلیغاتی را خالی نکند.

## ۷) صف Workerها (کنار Watcher و شماره‌گیر فعلی)

| Worker | کار | تیک |
|---|---|---|
| Watcher | کشف آگهی | اسکن |
| PhoneWorker | شماره | اکانت لاگین |
| SmsWorker | قالب sms به شماره‌دار | `sms_auto_on_new` |
| ChatWorker | قالب chat به فقط‌چت، per-platform | `chat_auto_on` |
| InquireWorker | قالب inquire | شکارچی + کلاس inquire |
| InboxWorker | خواندن چت + صندوق پیامک | اگر یکی از خودکارها روشن است |
| NluWorker | تحلیل پاسخ‌های جدید | همیشه قاعده؛ مدل اگر کلید باشد |

ChatWorker و InquireWorker از **یک** Chromium per-account به نوبت استفاده می‌کنند (قفل پروفایل) تا دو تب با هم قاطی نشوند.

## ۸) خروجی و پنل

علاوه بر شیت‌های قبلی:

- ستون `کانال ارسال`: chat_divar / chat_sheypoor / chat_ring / sms
- ستون `پاسخ خام` و `intent`
- فیلتر «پاسخ‌داده» / «در انتظار پاسخ» / «بدون پاسخ»

هشدار تلگرام ویژه فقط بعد از تحلیل موفق قیمت نقد سالم — نه بعد از صرف ارسال استعلام.

---

## ۹) ریسک و سقف — صادقانه

ارسال خودکار چت روی دیوار/شیپور/رینگ خلاف روح شرایط استفاده است و بن می‌سازد. برای محصول فروشی:

- پیش‌فرض تیک چت خودکار **خاموش**
- سقف سخت، متن با `{title}`، یک پیام per آگهی
- کپچا/محدودیت چت = توقف همان پلتفرم همان اکانت
- AI جواب آزاد بازاریابی نمی‌فرستد

بدون این سقف‌ها اشتراک یک هفته‌ای می‌میرد چون اکانت مشتری می‌سوزد.

---

## ۱۰) پیش‌فرض با «شروع کن»

1. چت خودکار مثل پیامک، تیک جدا، سه پلتفرم از Chromium همان پروفایل.
2. پیامک خودکار شماره‌دار همان ملی‌پیامک؛ صندوق ورودی پول می‌شود.
3. استعلام ویژه قالب جدا، یک کانال نه هر دو.
